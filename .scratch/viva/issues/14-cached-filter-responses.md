# 14: Cached filter responses

**What to build:** Running a viva again on unchanged code, with the same prompt version and model, reuses the stored filter response and makes zero provider calls. The mode indicator says "cached", distinct from "live" and "fallback". This protects the free-tier budget through dev, rehearsal, and judging, and lets a rehearsed demo replay if every provider is down. Cuttable: it serves success criterion #5 only.

**Blocked by:** 06

**Status:** done

**Type:** plumbing
**Spec:** brief §3.2 (caching by code hash), 09 §1 (label live vs. mock/cached explicitly)

- [x] The cache key covers prompt text, output contract, the functions' sources and candidate lists, and model id; any change is a miss.
- [x] A hit makes zero provider calls and is labelled "cached", naming the provider and model that originally served it.
- [x] The cache survives a page reload on the demo machine; where it lives is a Ruling here.
- [x] Rehearsals can clear it.
- [x] Force-fallback (ticket 06) wins over a cache hit.

## Comments

Ruling: the cache lives in the browser's `localStorage` (`src/llm/filter-cache-store.ts`), keyed by a SHA-256 hash of the request (functions' sources + candidate lists, already fully known client-side) plus prompt version, a hash of the prompt text, a hash of the output contract text, and the provider chain's `provider:model` signature (`src/llm/cache-key.ts` `buildFilterCacheKey`) — survives a reload on the demo machine, never touches the deployed function's ephemeral filesystem. Cost if wrong: swap the storage backend in one module (`filter-cache-store.ts`) without touching the key or the orchestration.

Ruling: the prompt text and output contract are server-only (loaded via `node:fs`, never bundled to the browser — ticket 06's Ruling that keeps `node:fs` out of the client bundle). Since the key needs their hashes and the chain's model ids, `api/filter.ts` grew a `{ metaOnly: true }` request shape that returns just `{ promptVersion, promptHash, contractHash, chainSignature }` without loading the chain or calling a provider — this lets the browser build the exact cache key and check for a hit *before* deciding whether to make a real filter call, which is what makes "zero provider calls" on a hit possible at all (a metaOnly round-trip to our own endpoint isn't a provider call). Cost if wrong: one extra fast round-trip per viva start when there's no prompt yet (metaOnly returns `available: false` and the caller falls through to a normal, uncached call).

Ruling: `callFilterApiCached` (`src/llm/client.ts`) is a new function alongside the untouched `callFilterApi` — App.tsx's `runViva` now calls the cached wrapper; `callFilterApi` itself, and ticket 06's tests against it, are unchanged. `FilterOutcome` (`src/llm/types.ts`) is a new client-side type (`FilterApiResponse | { mode: "cached"; ... }`) since the server never returns "cached" itself — it's synthesized in the browser when a stored response is replayed. Cost if wrong: rename/relocate one type if a later ticket wants the server aware of cache hits (e.g. for the candidate log).

Ruling: one filter call already covers every selected function (ticket 06), so the cache is per-viva, not per-function — a hit or miss is decided once for the whole batch, matching how `outcome.mode` already flowed through `App.tsx`'s `runViva` for "live"/"fallback". Cost if wrong: a mixed cached/live viva isn't representable; would need per-function keys and a per-function mode strip (already flagged as a possible follow-up in ticket 08's Rulings for the live/fallback split).

Ruling: added a "Clear cached filter responses" button next to the force-fallback checkbox on the start screen (`App.tsx`, `start.clearCache`/`start.clearCacheDone` in `en.ts`) so rehearsals can clear it, per the checklist. Cost if wrong: cosmetic, one button to move or remove.

## Answer

Built the cache key (`src/llm/cache-key.ts`, `buildFilterCacheKey`): SHA-256 (Web Crypto, works identically in Node and the browser) of the request's canonical JSON plus prompt version, prompt-text hash, contract-text hash, and the provider chain's `provider:model` signature — any change to a selected function's source/candidates, the prompt, the contract, or a provider's model id is a miss. Built the store (`src/llm/filter-cache-store.ts`): `localStorage`, namespaced `viva:filter-cache:`, survives a reload, best-effort (storage failures degrade to "no cache", never a broken viva), with `clearFilterCache()` for rehearsals (wired to a new button on the start screen). Extended `api/filter.ts` with a `{ metaOnly: true }` request shape that returns the cache key's server-only ingredients (prompt version/hash, contract hash, chain signature) without touching the provider chain — this is what lets a cache check happen before any provider call, not just before a *successful* one — and attached the same `cacheMeta` to every normal live/fallback-after-chain-exhausted response (`FilterApiResponse.cacheMeta`, additive/optional, ticket 06's response shape and tests untouched). Built the orchestrating seam (`src/llm/client.ts`, `callFilterApiCached`): force-fallback short-circuits straight past the cache (wins per the checklist); otherwise it fetches meta (zero provider calls), checks `localStorage` for a hit and returns `{mode: "cached", provider, model, result}` naming who originally served it; on a miss it calls the real endpoint and, if live, stores the result under the same key. `App.tsx`'s `runViva` now calls `callFilterApiCached` instead of `callFilterApi`, generalizing its existing "live" branch to "live or cached" (both carry the same `{provider, model, result}` shape) — one filter call still covers the whole viva (ticket 06), so a hit or miss applies to the whole batch, and the existing per-function "all loaded mutants were equivalent → fall back for that function alone" logic is unchanged and applies identically under a cache hit. `ModeIndicator.tsx` and `en.ts` (`mode.cached.detailWithProvider`) show the provider/model on a cached hit exactly as "live" already did. Verified with one real, unmocked NVIDIA call plus an offline test suite built from that real response (see Verification) — no mocked LLM response is presented as live; the client-side caching logic is exercised against a mocked `fetch`, which is the standard seam for testing browser networking code, not a stand-in for an unverified provider call.
